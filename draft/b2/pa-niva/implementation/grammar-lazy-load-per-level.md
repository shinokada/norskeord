# Lazy-load `grammar.json` per CEFR level

## Problem

`src/lib/data/grammar.json` is a single flat array covering all CEFR levels
(A1–C), now 33,000+ lines / 1MB+. Two separate pains:

1. **Content-authoring pain (this session's trigger):** any tool that reads
   the whole file (mine included) hits size limits and needs grep/tail
   workarounds for every topic-touch.
2. **Runtime/UX pain:** every route that imports `grammar.json` statically
   pulls in *all* levels' questions, even routes that only ever need one
   level (`/learn/[level]`) or one topic (`/grammar/[topic]`). For a learner
   working at A1, the B1/B2/C content is dead weight in their bundle.

## Decision: keep `grammar.json` as the single source of truth

Rejected: physically splitting `grammar.json` into `grammar-a1.json` /
`grammar-a2.json` / etc. as the *canonical* files. That would require
rewriting three things that all currently assume one file:

- **Admin editor** (`src/routes/admin/grammar/api/+server.ts`): GET/PUT the
  whole file in one GitHub commit via `readJsonFile`/`writeJsonFile`. Would
  need a multi-file-aware rewrite (which level(s) does an edited/added
  question belong to? cross-level topics like `spesial-kvantorer` complicate
  this) — out of scope for this task.
- **Validation scripts** (`scripts/check-{a1,a2,b1,b2,c}-grammar-vocab.mjs`,
  `check-grammar-norwegian.mjs`, `check-c-grammar-*.mjs`): all read
  `grammar.json` directly today. Splitting the source would mean rewriting
  every one of them to merge multiple files before checking.
- **This project's own content-authoring workflow** (every grammar
  topic-touch session, e.g. `b2-grammar-pa-niva-arbeidsbok.md`): edits
  target `grammar.json` directly via exact-text `edit_file` inserts. A
  cross-level topic (B1+B2, like `spesial-kvantorer`) would need edits to
  two files instead of one, plus the highest-ID/`plusOnly`-convention check
  would need to be run per-file.

**Chosen approach instead:** `grammar.json` stays the single file everyone
edits (admin, validators, this workflow — zero changes to any of them). A
build script derives the per-level split + a lightweight topic index as
**generated artifacts**, checked into the repo like any other build output,
regenerated by a script run after every content change.

## Derived artifacts

1. **`src/lib/data/grammar-{a1,a2,b1,b2,c}.json`** — `grammar.json`'s
   questions, filtered by `cefr`, each written as a flat `GrammarQuestion[]`
   array in the same shape as today. Order preserved (stable sort, original
   array order within each level).
2. **`src/lib/data/grammar-topic-index.json`** — one row per topic:
   ```json
   {
     "spesial-kvantorer": {
       "levels": ["B1", "B2"],
       "countsByLevel": { "B1": 10, "B2": 24 },
       "total": 34
     },
     ...
   }
   ```
   This is what lets `/grammar` (the topic picker) and `/grammar/[topic]`
   (the detail page) avoid loading *all five* level files just to answer
   "which levels does this topic span, and how many questions per level" —
   they read the tiny index instead, then fetch only the specific level
   file(s) a given topic actually needs.

## Generation script

`scripts/build-grammar-level-index.mjs` (new):

- Reads `src/lib/data/grammar.json`.
- Writes the 5 split files + the topic index.
- Exits non-zero if any split file's question count + index counts don't
  sum back to the original total (safety check).
- Wired into `package.json`'s `build` script, matching this repo's existing
  convention of explicit chaining (no npm `pre`/`post` hooks are used here —
  `build` already reads `"pnpm stats && vite build"`, so the new step joins
  that same chain rather than introducing an implicit `prebuild` hook):
  ```json
  "scripts": {
    "grammar:split": "node scripts/build-grammar-level-index.mjs",
    "build": "pnpm stats && pnpm grammar:split && vite build"
  }
  ```
  Order relative to `pnpm stats` doesn't matter for correctness —
  `scripts/generate-stats.mjs` reads `grammar.json` directly today (not the
  split files) for its per-level grammar counts, so the two scripts don't
  depend on each other. `grammar:split` just needs to run before `vite
  build`, since the split files are the actual import target for the
  routes listed below.
- Also exposed as its own `pnpm grammar:split` command so it can be run
  manually right after a content-editing session (before `pnpm dev`), the
  same way `pnpm stats` already is documented to be run after vocab/uttrykk
  changes.

## Call-site changes

Six non-test files currently import `grammar.json` directly (per
`grep -rln "grammar.json" src`):

| File | Current | Change |
| --- | --- | --- |
| `src/routes/grammar/+page.ts` | loads all questions, groups by topic across all levels for the picker | switch to `grammar-topic-index.json` only — it already has everything this route computes (`levels`, `countsByLevel`, `total` per topic); no full question objects needed here at all |
| `src/routes/grammar/[topic]/+page.ts` | loads all questions, filters by topic | read the topic's `levels` from the index, dynamically `import()` only those specific level file(s) (usually 1–2 of 5), merge, filter by topic |
| `src/routes/learn/[level]/+page.server.ts` | loads all questions, filters `q.cefr === levelUpper` | replace with a single dynamic `import()` of that level's file only — mirrors the existing `uttrykkThemeLoaders` pattern already in this exact file, just extended to grammar |
| `src/lib/stats.ts` | loads all questions once at module scope to build `grammarTotalsByLevel` (topic × level → count) | replace entirely with `grammar-topic-index.json` — `grammarTopicStatsForLevel` only ever needs the *counts*, never full question objects, so this becomes a pure win, no dynamic import even needed |
| `src/routes/admin/grammar/api/+server.ts` | reads/writes `grammar.json` in full via GitHub API | **no change** — admin editing stays against the single source-of-truth file, per the decision above |
| `src/lib/grammar/grammar-data.test.ts` | imports `grammar.json`, checks topic/rule integrity | **no change** — still validates the source of truth directly |

`src/lib/stats.test.ts` — check whether it mocks `grammar.json` or
`stats.ts`'s exports directly; update mocks only if they assert against the
old `grammarTotalsByLevel`-from-full-data internals.

## New loader helper

Add a small `grammarLevelLoaders` map (same shape as the existing
`uttrykkThemeLoaders` in `learn/[level]/+page.server.ts`) somewhere shared,
e.g. `src/lib/grammar/level-loader.ts`:

```ts
const grammarLevelLoaders: Record<CEFRLevel, () => Promise<{ default: GrammarQuestion[] }>> = {
  A1: () => import('$lib/data/grammar-a1.json') as unknown as Promise<{ default: GrammarQuestion[] }>,
  A2: () => import('$lib/data/grammar-a2.json') as unknown as Promise<{ default: GrammarQuestion[] }>,
  B1: () => import('$lib/data/grammar-b1.json') as unknown as Promise<{ default: GrammarQuestion[] }>,
  B2: () => import('$lib/data/grammar-b2.json') as unknown as Promise<{ default: GrammarQuestion[] }>,
  C:  () => import('$lib/data/grammar-c.json')  as unknown as Promise<{ default: GrammarQuestion[] }>
};
```

`/grammar/[topic]/+page.ts` calls this for only the levels the topic index
says it needs; `/learn/[level]/+page.server.ts` calls it for the one active
level.

## Migration steps

1. Write `scripts/build-grammar-level-index.mjs`.
2. Run it (`pnpm grammar:split`), verify the safety check passes (counts
   reconcile).
3. **Commit** the generated `grammar-{a1,a2,b1,b2,c}.json` and
   `grammar-topic-index.json` files like any other data file (resolved —
   see Decision on generation timing below; no `.gitignore` entry).
4. Add `src/lib/grammar/level-loader.ts`.
5. Update the three route/lib call sites (`/grammar/+page.ts`,
   `/grammar/[topic]/+page.ts`, `/learn/[level]/+page.server.ts`,
   `stats.ts`) one at a time, running existing tests after each.
6. Extend `grammar-data.test.ts` (or add a new test) asserting the split
   files + index are in sync with `grammar.json` (same reconciliation check
   as the generation script, so CI catches a forgotten regeneration before
   merge, even though `build` also regenerates them as a safety net).
7. Add `"grammar:split": "node scripts/build-grammar-level-index.mjs"` and
   update `"build": "pnpm stats && pnpm grammar:split && vite build"` in
   `package.json`.
8. Manual smoke test: `/grammar` picker loads and shows correct badges,
   `/grammar/[topic]` for a cross-level topic (e.g. `spesial-kvantorer`,
   B1+B2) loads both levels' questions correctly, `/learn/b2` hub shows
   correct grammar topic counts, `/stats` grammar breakdown unchanged.
9. Update this project's memory/process notes: `grammar.json` remains the
   canonical edit target for content sessions, so my existing
   `Filesystem:edit_file` workflow (exact-text inserts, grep-for-context
   via user-run Python/grep) is unchanged. What changes: after a content
   session, the split files are stale until either (a) someone runs `pnpm
   grammar:split` locally, or (b) the next `pnpm build` regenerates them
   automatically. **`pnpm dev` does NOT run `build`, so local dev will show
   stale grammar content after a content session until `grammar:split` is
   run manually** — flag this clearly as a new step in the content-session
   wrap-up, alongside the existing validator-script reminders.

## Decision: generation timing (commit + build-time regeneration, both)

Commit the generated files (keeps local `pnpm dev` correct without an
extra manual step *if* someone remembers to regenerate+commit) **and**
regenerate them unconditionally on every `pnpm build` (so a forgotten
regeneration never ships stale content to production, since the admin
editor's GitHub-commit-triggered Vercel deploy has no human in the loop to
remember the step). The CI staleness test (migration step 6) is a third
layer — it catches a stale commit in a PR review *before* merge, rather
than relying solely on the silent build-time overwrite to mask it.
